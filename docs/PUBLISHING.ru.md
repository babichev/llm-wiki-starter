# Как опубликовать шаблон и сохранить личную базу приватной

Публиковать можно этот нейтральный комплект, а не рабочий vault с личными знаниями. Перед созданием публичного репозитория владелец должен выбрать аккаунт, имя и подтвердить публичный доступ. Текущий архив сам ничего не публикует.

## Разделение хранилищ

Публичный репозиторий содержит мастер-промпт, нейтральные шаблоны, generic skills, код runtime, тесты и документацию. Новая личная база создаётся в другой папке и получает отдельную политику версионирования. Не меняй visibility существующего приватного репозитория ради передачи шаблона.

Публичный шаблон собирается из явно выбранных файлов в чистой папке с новой Git-историей. Не копируй `.git` рабочей базы. Даже удалённый из последнего коммита секрет может оставаться в её истории. `.gitignore` защищает только от части будущих добавлений и не очищает уже опубликованные данные.

## Проверка перед публикацией

Проверь именно итоговый набор файлов и архив:

- личные имена и адреса, локальные пути пользователей, контакты, реальные проекты и приватные ссылки отсутствуют;
- нет целей, доходов, семейного контекста, переписок, транскриптов, заметок встреч и журналов реальных запусков;
- нет `.env`, ключей, токенов, cookies, credential-файлов, OAuth callback с секретом, локального состояния коннекторов и резервных копий;
- примеры явно вымышленные и не попадают в рабочие профили;
- лицензия относится к собственному коду/текстам; чужие навыки не скопированы без проверки прав;
- документация не утверждает, что подключения или автоматизации уже настроены для получателя;
- тесты и структурные проверки прошли, известные границы описаны.

Автоматический поиск подозрительных строк полезен, но не заменяет просмотра содержимого и списка файлов. Проверяй также ZIP manifest: публичный каталог может быть чистым, а архив случайно включать соседние приватные файлы.

## Порядок публикации

Сначала подготовь чистый каталог и проверенный архив, чтобы владелец мог оценить конкретный материал. После разрешения создай новый репозиторий в выбранном аккаунте штатным инструментом или GitHub CLI, добавь только этот каталог и проверь список отправляемых файлов. Не используй широкое добавление из корня личного vault.

После загрузки открой репозиторий без привилегированного доступа, проверь README, основной промпт и несколько файлов по текущему commit. Сравни опубликованный набор с локальным manifest. До readback локальный commit или успешный push не считаются полной проверкой поставки.

Если права на публичное создание отсутствуют, передай ZIP и готовые материалы; не меняй приватный репозиторий обходным способом. Ссылка в сообщении другу появляется только после реального создания и проверки. Не выдумывай URL по предполагаемому имени.

## Сообщение после публикации

Когда реальный URL уже известен, замени им поле в таком сообщении:

```text
Сделай мне личную LLM Wiki по этому шаблону: [ВСТАВЬ ФАКТИЧЕСКИЙ URL].
Открой prompts/START-HERE.ru.md и выполни его. Сначала проверь возможности
среды и персонализируй систему под меня. Создай рабочие файлы, установи
доступные навыки и отдельно проверь подключения и регулярные обновления.
```

Квадратная вставка выше — явное место для действующего URL, не готовая ссылка. До публикации используй [сообщение с архивом](../prompts/SHARE.ru.txt).
